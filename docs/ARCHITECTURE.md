# Architecture

MemTab is a Manifest V3 Chrome extension with no build step, no dependencies, and no
network access. `src/` is the extension — what you load unpacked is what ships.

```
src/
├── manifest.json
├── shared/          logic with no browser dependencies, loaded by every surface
│   ├── _order.json      the load order, enforced by scripts/lint.mjs
│   ├── constants.js
│   ├── format.js        byte and duration labels
│   ├── palette.js       hex parsing, contrast, presets
│   ├── settings.js      defaults, validation, migration, storage access
│   ├── levels.js        reading + thresholds -> level, with hysteresis
│   ├── measure.js       performance.memory normalization
│   └── render.js        favicon geometry (pure) + a canvas executor
├── content/         the per-tab loop: measure, composite, apply, re-apply
├── background/      service worker: install defaults, backfill, favicon lookup
├── options/         the settings UI
├── popup/           per-tab status
└── icons/           generated by scripts/make-icons.mjs
```

## Where the work happens

**The content script owns the loop.** It measures, decides the level, composites the
favicon and applies it, all within the tab. The service worker is not in the hot path.

That is a deliberate reversal of the original prototype, which drove everything from
the background. Two platform facts make the background the wrong place:

- An MV3 service worker is terminated after 30 seconds idle, and its timers die with
  it. A `setInterval` there stops firing and nothing re-arms it.
- `chrome.alarms` — the sanctioned replacement — is extension-global rather than
  per-tab, and floors at 30 seconds once the extension is packed. The prototype polled
  every 5 seconds; alarms would have made it six times slower.

A timer inside the tab has neither problem.

**Settings reach every tab through storage, not messaging.** The options page writes to
`chrome.storage.sync`; `chrome.storage.onChanged` fires in the service worker, in every
open extension page, and in every injected content script simultaneously. There is no
broadcast loop, no `chrome.tabs.query`, and no tab that can be missed.

**The service worker does three things** a content script cannot: seed defaults on
install, inject into tabs that were already open, and look up a favicon for pages whose
icon is cross-origin. Every listener in it is registered synchronously at the top level
— see [Why listeners must be top-level](#why-listeners-must-be-top-level).

### `minimum_chrome_version`

Pinned to **110**, which is the highest floor anything in the codebase actually needs:

| Requirement | Landed in |
| --- | --- |
| Every extension API call resets the service worker idle timer, and the hard five-minute lifetime cap is gone | 110 |
| The `favicon` permission and the `_favicon/` endpoint | 104 |
| `chrome.storage.session` | 102 |
| `CanvasRenderingContext2D.roundRect()` | 99 |
| The CSS `:has()` selector, used by the options page style picker | 105 |

Raise it only when something genuinely needs a newer floor — every bump drops users.

## The shared-module pattern

Each file in `src/shared/` is an IIFE that hangs its exports off a `MemTab` global and
also exports via CommonJS at the bottom, guarded:

```js
(function (root) {
  'use strict';
  const MemTab = (root.MemTab = root.MemTab || {});
  // ...
  MemTab.levels = api;
  if (typeof module !== 'undefined' && module.exports) module.exports = api;
})(typeof globalThis !== 'undefined' ? globalThis : self);
```

Three details are load-bearing:

- **The IIFE is not decorative.** All of an extension's content scripts share one
  global lexical scope, so a top-level `const MemTab` in two files is a redeclaration
  `SyntaxError`.
- **The `module.exports` guard is not optional.** `module` is undefined in a content
  script, in a classic service worker, and on an extension page. An unguarded
  `module.exports` throws at evaluation and takes that whole surface down — inside
  `importScripts()` it aborts service-worker startup. `scripts/lint.mjs` checks for it.
- **The load order is repeated in five places** (`_order.json`, `constants.SHARED_FILES`,
  the manifest, the service worker's `importScripts()`, and two HTML pages). That is the
  cost of having no bundler, and `scripts/lint.mjs` asserts all five agree. Adding a
  shared module means updating all of them; the lint will tell you if you miss one.

Content scripts declared in the manifest cannot be ES modules, which is what forces the
classic-script style. The same style is used everywhere else for uniformity.

## What MemTab actually measures

This is the most important section in this document, and the thing most likely to
generate bug reports.

MemTab reads **`performance.memory`**, a non-standard Chrome API. It reports the V8
JavaScript heap for the *renderer process* serving the page.

Of the three fields it exposes, MemTab levels and displays **`totalJSHeapSize`** — the
heap V8 has actually allocated — not `usedJSHeapSize`, which counts live objects.
`used` sawtooths with garbage collection (it climbs while garbage accumulates and drops
at every major GC), so a colour keyed to it flickers on GC cycles rather than tracking
real growth; `total` is the envelope of that sawtooth and the closer of the two to what
the tab costs the machine. This is what the original prototype shipped, and the one
place allowed to make that choice is `measure.metric()` — `levels.classify()` and the
popup both go through it, so the tab colour and the headline number cannot disagree.

Consequences:

**It is not the tab's memory.** It covers JS objects and V8 external memory
(`ArrayBuffer` backing stores, WebAssembly), and excludes the DOM, images, decoded
bitmaps, canvas and the compositor — usually most of what a tab really costs. A tab
holding 3 GB of decoded images can read 40 MB. Real tab memory is typically two to four
times the JS heap.

**Same-site tabs share it.** Chrome's process-per-site-instance model puts tabs on the
same site in one renderer, sharing one V8 isolate and therefore one reading. Ten GitHub
tabs will all show the same number and all turn red together if one of them leaks. This
gets *more* aggressive under memory pressure — i.e. exactly when someone would install
this.

**Background tabs update slowly.** Chrome clamps hidden-tab timers to about one fire per
minute after five minutes hidden, may freeze the page entirely under Energy Saver, and
may discard it under Memory Saver. A background tab's colour can be minutes old, and a
discarded tab keeps whatever icon it had when Chrome unloaded it.

**It can be coarsened.** Chrome reports precise values only when the renderer is locked
to a site. That is the normal case on desktop, where full site isolation is on, but
where it isn't the values are snapped to ~6% buckets with a 10 MB floor and refreshed
only every twenty minutes. `measure.looksBucketized()` detects this and the popup says
so rather than showing a fabricated number.

MemTab is honest about all of this in the options page and the popup. It is a good leak
detector for the tab you are on and a poor triage tool for forty background tabs — for
that, Chrome's own Task Manager (<kbd>Shift</kbd>+<kbd>Esc</kbd>) reads the real
per-process figure.

### Why not something better?

| API | Why not |
| --- | --- |
| `performance.measureUserAgentSpecificMemory()` | The sanctioned replacement, and far better data — but it is only exposed on cross-origin-isolated pages (COOP + COEP). An extension cannot impose that on third-party sites, so on an ordinary page the function simply does not exist. It also waits for a garbage collection, resolving 10–20 seconds later. |
| `chrome.processes` | Real per-process private memory, which is what we actually want. The permission is gated to the Dev channel in Chromium's `_permission_features.json`, with a hard-coded allowlist for beta/stable that no third-party extension is on. On stable it is silently dropped at load with a permanent warning on the extensions page, and `chrome.processes` is `undefined`. See [`archive/poc/b-processes-api/`](../archive/poc/b-processes-api). |
| `chrome.system.memory` | Stable, but system-wide only. No per-tab granularity at all. |
| `chrome.debugger` + CDP `Performance.getMetrics` | Genuinely stable and per-tab, but still JS-heap-only, and it shows a permanent "MemTab started debugging this browser" bar on every attached tab. Not worth it. |

There is no stable-channel Chrome extension API that reports per-tab physical memory.
Chrome's own tab hover cards show it because they read the Task Manager internally,
which is not exposed to extensions.

## The favicon pipeline

Composite once per page, swap synchronously thereafter.

1. **Pick a source icon** from `<head>`: an SVG icon, else the largest declared
   `sizes=`, else `apple-touch-icon`, else `/favicon.ico`.
2. **Load it without tainting the canvas.** Same-origin icons load directly — the common
   case, no round trip and no permissions involved. Cross-origin icons would taint the
   canvas and make `toDataURL()` throw, so those go through the service worker.
3. **Composite all three levels** onto a 32×32 canvas and keep the data URLs in memory.
4. **Apply** by appending a `<link rel="icon" sizes="any">` to `<head>`.
5. **Re-apply** when the page overwrites it, from the cached href, synchronously.

Level changes after step 3 are a pure `link.href` swap with no async work anywhere.
That is what lets the MutationObserver win against a single-page app that rewrites its
own favicon on every route change — if re-applying had to await a message round trip,
it would be permanently one hop behind.

### Sizing

Composites are 32×32, never 16×16. Chrome's tab strip wants 16 DIP at 1× and 2×, i.e.
16px and 32px bitmaps, and `select_favicon_frames.cc` resamples with nearest-neighbour
whenever the target is an exact integer multiple of the source and Lanczos3 otherwise.
So a 16px source pixel-doubles into a deliberately blocky 32px representation — that is
the pixelation the prototype hit. At 32px the 2× representation is an exact match and
the 1× is a clean downscale.

### Why the service worker uses `_favicon/` rather than fetching the icon

The obvious implementation is: read `<link rel=icon href>` off the page, `fetch()` it in
the service worker (which bypasses CORS with host permissions), and hand the bytes back.

Don't. That URL is page-controlled. Fetching it from the worker and returning the result
into the page's own DOM is a cross-origin read primitive: a hostile page sets
`<link rel="icon" href="http://192.168.1.1/admin">`, MemTab fetches it past the user's
network boundary, and the page reads the bytes back out of the `href` it now owns.

Instead the worker reads Chrome's own favicon database through
`chrome-extension://<id>/_favicon/?pageUrl=…`, using `sender.tab.url` — populated by
Chrome, never by the message body. That endpoint is same-origin to the worker, needs no
host permission, and makes no network request. The quality is a little worse than
fetching the real icon. That is a fine trade.

`_favicon/` is deliberately **not** in `web_accessible_resources`. Exposing it to pages
would turn Chrome's favicon database into a browsing-history oracle any site could probe
by timing. `scripts/lint.mjs` fails the build if it ever appears there.

## Why listeners must be top-level

When Chrome revives a terminated service worker it re-runs the script from the top and
then dispatches the queued event. A listener registered after an `await`, inside a
`.then()`, or inside a function is not present in that first synchronous turn, so the
waking event is dropped — the handler works in a fresh session and then mysteriously
stops.

Registering listeners *inside* a function that runs repeatedly is worse, and is the bug
in [`archive/poc/b-processes-api/background.js`](../archive/poc/b-processes-api/background.js):
`chrome.processes.onUpdatedWithMemory.addListener()` was called inside `checkMemory()`,
which ran on every tab activation and every interval tick. Chrome does not deduplicate,
so the listener count grew without bound and one event fired N handlers.

## Testing

`npm test` runs `node --test` over `src/shared/`. Everything there is pure, which is why
it is where the logic lives: threshold banding and hysteresis, settings validation and
clamping, colour parsing, favicon geometry, and the bucketized-mode heuristic.

`render.js` is split into `plan()` (pure geometry, returns shapes and an icon box) and
`paint()` (a thin executor that applies them to a 2D context) specifically so the
geometry is testable — that the icon box never leaves the canvas, that ring and plate
inset the icon rather than drawing over it, that the bar's *length* encodes the level.

`npm run lint` covers the extension-specific invariants a general linter cannot know:
shared-module load order across all five load sites, guarded `module.exports`, every
manifest-referenced path existing, version sync between `package.json` and the manifest,
`_favicon/*` never being web-accessible, and no broken relative links in the docs.

What neither catches: the tab strip's actual rasterization, real memory pressure, and
the behaviour of specific sites. Those need a manual pass — see
[CONTRIBUTING.md](../CONTRIBUTING.md#what-ci-can-and-cant-catch). A headless-Chrome
smoke job would close most of that gap and is an open issue.
