# Publishing MemTab to the Chrome Web Store

Everything needed to go from this repository to a published listing, in order.

All the copy is pre-written in [`store/listing/`](../store/listing) and all the images are
generated by `npm run store-assets`. The work is mostly pasting.

> **Requirements change.** This was written on 26 July 2026 against the live docs. Before
> submitting, skim [Chrome Web Store program policies][policies] and the
> [developer blog][blog] — a policy update taking effect **1 August 2026** is covered
> under [Before you submit](#before-you-submit).

---

## 1. One-time account setup

You only do this once, but two of these steps are irreversible, so read before clicking.

1. **Pick the Google account carefully.** Go to the
   [Developer Dashboard][dashboard] and register. Google's docs are explicit:
   *"After an account is created, you cannot change its email address."* A deleted
   account's email can never be reused for a new one either. Use a dedicated account
   rather than your personal one if you might ever hand the project over.

2. **Turn on 2-Step Verification** on that account. Once 2SV enforcement applies to your
   account you cannot publish or update anything until it's enabled. Do it now rather
   than discovering it mid-submission.

3. **Pay the one-time registration fee.** The amount is *not* published in the docs — the
   developer agreement says only "a one-time registration fee, in an amount determined in
   Google's sole discretion". It has historically been USD 5. Check the figure on the
   payment screen.

4. **Set your publisher name** on the Account page. It appears under the title on every
   listing you publish.

5. **Verify a contact email.** Account → Add email → request verification → click the
   link. This is required before you can publish.

6. **Declare Trader or Non-Trader status.** Required of every developer, driven by the EU
   Digital Services Act. Google will not tell you which you are — *"Each publisher must
   make their own determination."* Be aware that declaring **Trader** requires a legal
   name, physical address and SMS-verified phone number, and **all of it is published
   publicly at the bottom of your listing**. A free, non-commercial extension is
   ordinarily Non-Trader, but this is a legal determination, not a technical one.

A physical address is otherwise only required if the item offers purchases or
subscriptions, which MemTab does not.

## 2. Host the privacy policy

The store requires a **linkable URL**, not text pasted into the description. Putting the
policy in the description instead of the field is a listed rejection cause.

The policy is served from the marketing site:

```
https://memtab.fixit.works/privacy
```

Use that URL on both listings. A GitHub blob URL also works but breaks if the repo is
ever renamed or moved, and the store keeps whatever you gave it.

The page is [`site/privacy.html`](../site/privacy.html); [`PRIVACY.md`](../PRIVACY.md)
is the same text for people reading the repo.

## 3. Build the package

```bash
npm run check && npm run build
```

That produces `dist/memtab-<version>.zip`. Three things worth knowing:

- **`manifest.json` must be at the zip root**, not inside a folder. `scripts/build.mjs`
  already writes entries relative to `dist/memtab/`, so this is correct — but if you ever
  zip by hand, zip the *contents* of the folder, not the folder.
- **The version in `package.json` is the source of truth.** The build writes it into the
  manifest and `npm run lint` fails if they disagree.
- **A published version number is burned forever.** You can never re-upload the same
  version, and rolling back does not free the old number — you republish the old code
  under a *higher* one. Leave yourself headroom.

Extension versions are dotted integers only. A semver prerelease like `0.2.0-beta.1` in
`package.json` is an illegal manifest version, and the build refuses it rather than
silently stripping it.

## 4. Generate the listing images

```bash
npm run store-assets
```

Writes everything to `dist/store/`, each at the exact size the store requires:

| File | Size | Status |
| --- | --- | --- |
| `store-icon-128.png` | 128×128 | **Required** |
| `screenshot-1-tabstrip.png` … `screenshot-5-honest.png` | 1280×800 | **Required** (1–5; all five are provided) |
| `promo-small-440x280.png` | 440×280 | **Required** |
| `promo-marquee-1400x560.png` | 1400×560 | Optional — needed to be eligible for the store homepage carousel |
| `social-card-1200x630.png` | 1200×630 | Not a store asset; the marketing site's Open Graph image |

Notes:

- Screenshots may be 1280×800 **or** 640×400. 1280×800 is preferred and is what we
  generate. Square corners, full bleed, no padding.
- The store icon should have its artwork inside a 96×96 area with 16px of transparent
  padding on each side.
- Promo tiles **cannot be localised**; screenshots can.
- Two of the screenshots embed the real options page and popup in an iframe rather than a
  pasted bitmap, so they cannot drift from the shipping UI. Re-run this command whenever
  the UI changes.

## 5. Fill in the listing

Upload the zip first (Items → Add new item), then work through the tabs.

### Store listing tab

| Field | Where the text is | Limit |
| --- | --- | --- |
| Name | `src/manifest.json` → `name` | 75 characters |
| Summary | `src/manifest.json` → `description` | **132 characters**, plain text |
| Description | [`store/listing/description.md`](../store/listing/description.md) | No documented limit |
| Category | **Developer Tools** | Pick one |
| Language | English | |

`npm run lint` checks the name and summary lengths so you can't overrun them by accident.

**Category:** Chrome defines Developer Tools as *"Extensions that help web developers
perform tasks like debugging, performance analysis, code linting…"* — performance
analysis is named explicitly, so this is the right fit. You pick **one** category; there
is no documented secondary. *Functionality & UI* would be the alternative if you were
aiming at general users rather than developers.

No rich formatting is documented as supported in the description, so
`description.md` is written to read correctly as plain text.

### Privacy practices tab

This is where most first submissions get stuck. Four things:

1. **Single purpose description** — paste
   [`store/listing/single-purpose.txt`](../store/listing/single-purpose.txt). There is no
   prescribed wording; the goal is to state a narrow, easily-understood purpose.

2. **Permission justifications** — the dashboard generates one field per permission in
   your manifest, host permissions included. Paste the matching block from
   [`store/listing/permission-justifications.md`](../store/listing/permission-justifications.md).

   If you see a field for a permission you don't recognise, **remove it from the manifest
   and upload a new version** rather than writing a justification for it. Unused
   permissions are a rejection cause in their own right.

3. **Remote code** — select **"No, I am not using remote code."** True for MemTab: no
   external scripts, no `eval`, no bundler, no minification. Extensions that use remote
   code without declaring it are rejected outright.

4. **Data usage disclosures and Limited Use certification** — tick the data types you
   collect (for MemTab: none) and complete the certification. You cannot submit without
   this.

5. **Privacy policy URL** — the URL from step 2.

### Distribution tab

- **Visibility:** Public, Unlisted, or Private. **Unlisted** is worth considering for a
  first release — the item is live and installable by link but isn't listed or searchable,
  so you can shake out problems before it's discoverable.
- **Percentage rollout is not available to you at launch.** It requires more than 10,000
  seven-day active users. The controls also only appear *before* you submit and are
  disabled afterwards.

## 6. Before you submit

A last pass, in rough order of how likely each is to bite.

- [ ] **Read the [1 August 2026 policy update][blog].** It tightens Limited Use to data
      "strictly necessary to the extension's disclosed single purpose" and requires
      prominent disclosure of *all* data handling, plus notification if practices change
      after install. A local-only extension should sail through, but check your
      disclosure wording against the new text rather than assuming.
- [ ] `npm run check` passes.
- [ ] Manifest version bumped, and higher than anything ever published.
- [ ] Load `dist/memtab/` unpacked and click through it one final time. A reviewer opening
      a page where the indicator doesn't visibly appear can reject under "functionality
      does not match the listing description".
- [ ] Description's "what it measures" section still matches reality.
- [ ] Every screenshot shows the current UI (`npm run store-assets` re-run).
- [ ] Privacy policy URL resolves.

### What actually gets extensions rejected

Worth knowing which of these apply to MemTab:

| Cause | MemTab's exposure |
| --- | --- |
| Obfuscated code | **None.** Minification is allowed; obfuscation isn't. MemTab ships unminified, unbundled source. Say so in the reviewer notes — it removes the single biggest source of review friction. |
| Remote code | **None.** Nothing is fetched or evaluated. |
| Broad host permissions | **High.** `http://*/*` + `https://*/*` draws scrutiny and can push the item out of fast self-serve review. This is why the justification explains what the access is *not* used for. |
| Unused permissions | **None**, and `npm run lint` fails the build if an unused one creeps in. |
| Functionality not working | **Moderate.** A reviewer landing on a page where extensions can't run, or a site whose CSP blocks generated favicons, sees nothing happen. Mitigate in the reviewer notes — see below. |
| Bundled unrelated features | **None**, provided the options page stays focused. Don't add tab management. |
| Privacy policy missing or in the wrong field | Avoidable; see step 2. |

**Reviewer notes worth including:**

> MemTab is unminified, unbundled source with no dependencies and no remote code; the
> uploaded package is byte-identical to https://github.com/councilOfNine/memtab
>
> To see it working: install, open any ordinary https page, and **reload it** — content
> scripts don't apply to tabs that were already open before install. The coloured ring
> appears on the tab's favicon. Set "Also mark healthy tabs" in the options page to see
> the indicator immediately rather than waiting for a threshold to be crossed.
>
> The indicator cannot appear on chrome:// pages, the Web Store, or the PDF viewer, and
> some sites' Content-Security-Policy blocks generated favicons — the toolbar popup
> reports which case applies on any given page.

## Microsoft Edge Add-ons

Edge is free, Chromium, and takes the same package unmodified. The full plan is in
[ROADMAP.md](ROADMAP.md#phase-2--microsoft-edge-add-ons); the differences from Chrome
that matter while you're in the form:

| | Chrome | Edge |
| --- | --- | --- |
| Registration fee | one-time | **free** |
| Store logo | 128×128 | **300×300** (`store/assets/edge-logo-300.png`) |
| Description | no documented limit | **250–10,000 characters** |
| Screenshots | 1280×800 or 640×400, max 5 | 1280×800 or 640×480, **max 6** |
| Promo tiles | 440×280, 1400×560 | same sizes |
| Name / summary | from the manifest | from the manifest (read-only in Partner Center) |
| Review | days → weeks | **≤ 7 business days** |

Two Edge-specific things:

- **Do not reference other browsers in the UI.** Edge developer policy 1.1.2 forbids it,
  and policy 1.5.2 says the privacy policy should primarily refer to Edge. MemTab's UI is
  already browser-neutral for this reason.
- **Verify the `favicon` permission works on Edge before you register.** It is not in
  Microsoft's documented permission list. Sideload the package via `edge://extensions`
  and confirm a site with a CDN-hosted favicon still composites correctly.

The single-purpose statement, permission justifications and remote-code answer are the
same as Chrome's — reuse [`store/listing/`](../store/listing).

## 7. Submit, and wait

Review time is officially *"a few days, but it can take up to a few weeks"* — and the
review-process page currently carries a banner about a submission surge since April 2026
causing extended times. A first submission with broad host permissions is on the slow
path. Plan for weeks.

You can cancel a submission while it's pending if you spot a problem.

---

## 8. Updating later

1. Bump `version` in `package.json`.
2. Add a `CHANGELOG.md` entry.
3. `npm run check && npm run build`.
4. Upload the new zip, then submit.

Things that surprise people:

- **Manifest metadata is not editable in the dashboard.** Fixing a typo in the name or
  summary means uploading a new version.
- **Rollback discards pending work.** Any staged or under-review submission is thrown
  away, and Chrome's own docs warn rollback "has the potential to break your extension,
  or cause data loss" — backward compatibility of anything in `chrome.storage` is your
  problem. `Settings.sanitize()` is what protects MemTab here: it accepts any shape and
  clamps it, so an older build reading newer settings degrades rather than breaks.
- **Comments in `manifest.json` cause "Cannot parse the manifest".** The build
  re-serialises through `JSON.parse`/`stringify`, so the generated package is safe — but a
  hand-edited zip is not.

## 9. After publishing

- **Respond to store emails.** Failing to respond to actionable Chrome Web Store emails
  can get the item removed, and a removed extension is disabled in users' browsers and
  cannot be re-enabled by them.
- **Respond to reviews** from the dashboard. For a developer tool, a public reply
  explaining the JS-heap caveat will save you the same conversation repeatedly.
- **Appeals are effectively one-shot** and are disabled entirely if your publisher account
  is suspended — resolve any account issue first.
